# BreezeTravel「行程查」产品章程

> 状态：`ACCEPTED`
>
> 章程版本：`Blueprint 1.0`
>
> 生效日期：2026-08-27

## 1. 为什么建设

旅行组织者常常已经有一份来自攻略、群聊、朋友或 AI 的计划，但很难判断它是否真的能走：文本混有介绍、备选和旧方案；地点可能重名或错城；路线、营业、预约、住宿和用餐衔接容易被忽略。

「行程查」不从空白开始生成一篇攻略。它先把用户已有内容整理成可编辑的逐日行程，再用真实地点、路线和时效证据指出少量最重要的问题，并提供最小改动的解决方式。

## 2. 产品承诺

> 用户粘贴攻略或上传截图，不填写前置表单，也不理解项目术语；系统自动生成高准确率的逐日行程卡片，提前准备路线地图，再用少量、可靠、可直接采纳的建议帮助用户把行程变得真正可执行。

用户得到：

- 按天组织、可以查看和编辑的行程卡片；
- 地点、步行/公交路线和住宿衔接；
- 最多 3 个“必须调整 / 可以更好 / 需要确认”的重点问题；
- 有真实依据的候选和最小修改方案；
- 修改后的新行程版本与完整复检。

## 3. 用户只看到什么

普通用户只看到地点名称、类别、地址、可靠的营业/预约提示、路线、住宿和餐饮建议，以及查看、替换、删除、插入、排序、更新地图和采纳建议。

普通用户不看到原文映射、source span、置信度数字、UID、hash、revision、receipt、模型、Provider、Brief、Evidence、Audit、Repair、Postcheck 或内部错误。

内部证据仍完整保留，但只能服务回归、追责、诊断和证据回读。它不得通过公共结果 API、DOM、隐藏文案或错误详情泄漏给用户。

## 4. 入口、假设与范围

- 核心用户：承担朋友或家庭行程整理与核验压力的组织者。
- 输入：粘贴文本、手工文字，以及后续版本的 PNG/JPEG/WebP 截图。
- 地理范围：解析任意国内城市；北京、上海、杭州提供深度地点、路线、知识和核验能力。
- 行程形态：优先单城市；跨城内容可以忠实整理，但不得伪装成已经通过跨城深核验。
- 日期：缺失时保留 Day 1、Day 2，不伪造日历日期或具体天气结论。
- 人数：缺失时软默认 2 人，不要求确认后才能生成卡片。
- 城市：缺失时采用概率最高城市作为可编辑工作假设。
- 天数：优先尊重原文日结构；完全没有结构时默认三天。

手机号验证码是主登录入口，邮箱为备用；未登录用户可通过固定示例体验。新首页不再以房间号、城市卡片、天数和人数表单作为入口。

## 5. 成功标准

北极星是：用户以很少的确认操作，把杂乱输入变成一份愿意继续查看、能够实际执行的行程。

候选版至少证明：

- 描述句、URL、预约说明不会成为地点卡片；
- 错城或错类别地点不会自动进入行程；
- 高置信地点自动匹配，低置信内容局部待确认且不阻断；
- 首批卡片快速出现，地图在后台准备；
- 卡片修改不会触发隐藏的实时路线重算；
- 地图、住宿和 Audit 均绑定明确 revision；
- 报告一次只呈现3个最高价值问题；其余未解决硬问题保留队列并明确数量，不得显示已通过；
- 自动、Provider、浏览器、真人和商业证据分别披露。

版本学习指标使用最小、无原文的事件或研究回执：卡片生成完成率、首次有用卡片时间、自动匹配后的用户纠正率、地图打开/手动更新率、住宿候选选择率、建议采纳后保留率、分享后的有效行程查和同一行程回访率。它们用于发现体验问题，不替代正确性Gate、真人可用性或付费证据；`public_resource_id`、匿名capability、原文、地点内容和身份字段不得进入分析事件。

G01激活时冻结卡片指标的事件版本、分母和7/30天窗口；G02冻结地图/住宿指标；G03冻结建议采纳后保留；G06冻结分享与回访。口径变更创建新版本，不能把不同口径拼接成提升。

详细门槛见 `../governance/RELEASE_GATES.md`。

## 6. 产品原则

1. 先给可用卡片，再询问真正影响结果的局部问题。
2. 映射过程内部可追溯，对用户完全隐藏。
3. 自动地点匹配优先保证精度，覆盖率不足时保留待确认。
4. 地图后台预计算，修改后由用户手动更新。
5. 没有酒店是待补全，不是错误。
6. 硬事实来自 Provider 与规则；模型只做语义提案和表达。
7. 任何语义编辑产生新 revision；旧地图和报告立即 stale。
8. `UNKNOWN` 与 `UNAVAILABLE` 不得包装成 PASS。
9. 产品声明永远不超过当前 commit 的证据等级。

## 7. 理想版本

- `CORE_MVP`：V0.1长文本可信卡片 → V0.2真实地图与整程住宿 → V0.3 Top-3可行性核验。
- `PRODUCT_ENHANCEMENT`：V0.4截图一致性 → V0.5三城有来源知识 → V0.6显式记忆与分享。
- `CANDIDATE_HARDENING`：V0.9在同一候选commit完成性能、隐私、可靠性和演示收口。
- V1.0：经单独批准的小规模真人可用性证据。

G01～G03按上述顺序推进；G03完成后固定停在`CORE_MVP_OWNER_REVIEW_PENDING`，项目所有者完成体验验收前不得激活G04。G04～G07只有在该验收后才按顺序推进，G07完成后停止。H1、部署、公网、生产、商业和`main`合并始终需要项目所有者单独批准。

商业探索只能在真人价值成立后独立立项，优先验证单次深度核验和创作者工具，不预设低频订阅。

## 8. 当前不做什么

- 不恢复房间号、Builder 或从零拖拽规划作为主入口。
- 不新增运行时多 Agent、消息队列、Kubernetes、GraphRAG 或重新微调模型。
- 不抓取未授权社交内容，不把模型常识写成当前事实。
- 不承诺实时客流、医疗安全、自动订票、最低价、房态或全国深核验。
- 不用测试数量、历史 Candidate、代理 Judge 或公开演示代替真人与商业证据。
