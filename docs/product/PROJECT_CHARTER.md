# BreezeTravel「行程查」产品章程

> 状态：`ACCEPTED`
>
> 生效日期：2026-08-22
>
> 产品名称：行程查
> 内部技术名称：行程核验

## 1. 为什么建设

朋友或家庭的小团体往往已有一份来自 AI、攻略或群聊的行程，但很难确认它是否真的能走：地点可能重名或错城，营业与预约信息会变化，交通和酒店往返时间容易被忽略，成员偏好、体力、天气和临时风险也常散落在对话里。

「行程查」不负责重新生成一篇漂亮攻略，而是把已有计划变成一份可核验、可调整、可追溯的行程版本。

## 2. 产品承诺

> 从不受控文本或截图中忠实抽取任意国内单城市行程需求；经用户确认精确城市、日期与人数后，核验地点、时间、交通、住宿、偏好、强度、天气和潜在风险，并为每个问题提供可执行的调整方式或有真实依据的备选地点。

用户最终得到：

- 已确认的本次行程条件与偏好；
- 按「必须调整 / 建议优化 / 待确认」分组的核验报告；
- 每个非 PASS 问题至少一条可执行行动建议；
- 有可靠候选时的真实备选地点及路线变化；
- 每次采纳都形成新 revision，并经过完整复验；
- 每项事实、风险和候选可追溯到对应 evidence/receipt。

## 3. 核心用户与范围

- 用户：为朋友或家庭承担行程核验与协调压力的旅行组织者；
- 同行人数：解析任意表达；核验前确认正整数，不设产品上限；
- 行程长度：解析任意表达；核验前确认完整日期范围，不设产品上限；
- 城市：任意国内城市；
- 形态：单城市国内自由行；
- 输入：粘贴文本、手工文字、PNG/JPEG/WebP 截图。

多城市、范围、约数或未知值在 Intake 中忠实保留；未确认成单一国内主城市、完整日期范围和正整数人数时不得进入事实核验。跨城行程仍返回结构化阻断，不静默降级。

## 4. 成功是什么

北极星结果是：用户用更短时间得到一份关键风险已确认、符合本次同行条件、可以实际执行的行程版本。

V1 内测候选版的产品成功由以下事实共同证明：

- 关键字段能正确抽取，低置信内容不会未经确认进入权威行程；
- 地点和路线错误不被自动接受，硬冲突不漏报；
- 非 PASS 问题都有明确行动建议，地点候选真实且有 receipt；
- 修改后不会引入新的高风险问题；
- 相同 snapshot 可重放，断线/重启/并发/幂等行为稳定；
- 自动证据、真实 Provider 证据与真人反馈分别报告。

详细指标与门禁以 `../governance/RELEASE_GATES.md` 为准。

工程交付同时服务 AI 应用与可靠后端岗位的面试证据，但面试目标不得降低产品正确性、隐私、真实来源或真人 consent 门禁。技术关键词、历史测试和公开演示均不能替代用户主链与对应证据。

## 5. 当前不做什么

- 不建设拖拽式从零路线生成器；现有 Builder 仅保留代码与最低回归。
- 不支持一个 workspace 内跨城行程。
- 不新增 Agent、消息队列、Kubernetes、GraphRAG，不重新微调模型。
- 不承诺实时客流、精确拥挤度、医疗安全、自动订票、最低价格或全平台库存。
- 不把模型推荐、社交内容或历史 RAGAS 分数当作当前事实。
- 不在 V1 候选版 Gate 中提前计入真人内测证据；真人内测是 G0～G6 通过后的 H1 独立阶段。

## 6. 产品原则

1. 先确认输入，再核验事实。
2. 不确定就是 `UNKNOWN`，不可用就是 `UNAVAILABLE`。
3. 硬事实与建议判断分栏呈现。
4. 先给行动方式，再给真实候选。
5. 修改产生新版本，解决状态来自完整复验。
6. 当前行程确认优先于长期档案；推断不成为 HARD。
7. 产品声明永远不超过当前 commit 的证据等级。

## 7. 长期方向

V1 和真人内测证明价值后，可以独立立项评估：更多合规输入来源、临行前增量复检、多人确认体验，以及将稳定的核验能力抽成 API/SDK。跨城和从零 Builder 仍需要新的用户证据、成本评估与人工批准，不能视为自然续期。
