# 无日期具名酒店恢复方案

状态：**已实现；原输入的恢复、删源、地图、选择与撤销真实往返通过。** 2026-09-07。
本文件记录当前实现边界，不替代产品定义、实施计划或当前状态。搜索缺城市、旧摘要禁用新候选、选择第一晚时丢失第二晚身份均已修复，原v1–v4失败保留。最终v5同原输入的19项恢复流程、12项选店与撤销、5项单日地图检查通过，截图与内部地点事实已独立核对；三种用途及隐私竞争另由受控页面/真实数据库覆盖。v5仅验证用户明确指定第二晚的一个开发样本，不能替代整体模型准确率或全部用途真实验收。

## 用户结果与范围

酒店名称和原文引用已核对，但住宿用途或日期补全失败时，保留可恢复对象。用户无需重新输入酒店，可明确它是全程住宿、某晚住宿或仅到访，再核验具体门店。

- 不虚构 Day1 访问，不恢复未确认主卡，不将未知酒店自动当全程住宿，也不据此阻断其他夜晚的住宿建议。
- 仅保留名称、引用有效的具名酒店；错误引用、无名“住宿未定”、纯介绍和备选不通过本入口变成主线。
- 不增加模型调用。用途由用户明确补充，不将用户确认冒充模型已读懂原文。
- 不迁移历史酒店含义，不扩展原文保留期限或公共原文范围。

## 用户路径

1. 在“待确认地点”的展开区域显示“酒店名称 · 住宿用途待确认”。名称通过私有补充接口按需读取。
2. 选择“全程住宿”“指定夜晚”或“仅到访”。指定夜晚使用现有行程夜晚；仅到访需选日期和位置。未选择不默认任何一种。
3. 用户主动搜索并选择具体门店。改变用途、夜晚或插入位置后，清空旧候选选择。
4. 最后一次确认同时保存门店和用途。失败保留待确认入口；取消或关闭零写入。
5. 全程／指定夜晚在独立住宿区域展示；仅到访在用户指定日期和位置形成已确认卡片。均支持刷新、撤销和版本冲突恢复。

## 数据与识别投影

主要位置：`backend/app/trip_understanding/experience_inference.py`、`models.py`、`pipeline.py`。

- 当前 `MISSING_EXPLICIT_DAY` 会使整个酒店项进入无效集合。仅当名称和引用有效、剩余问题是酒店日期／用途时，保留 `ProposedMention.day_index=None`，标记待确认；绕过默认 Day1 分支。
- 复用 `trip_understanding_activities`：现有表允许 `day_index=NULL`、`eligible_for_place_search=false`。保留随机令牌及既有源引用，不需要新数据表。该对象不执行自动 POI 搜索，不投影为主卡或地图站点。
- `UserFacingTripResult` 追加默认空的 `pending_lodgings`，只保存随机令牌、待确认状态和可归属于该对象的问题计数／类别，不保存名称、引文、偏移或位置派生 ID。
- 已确认的全程／指定夜晚使用独立 `lodging_constraints`，包含明确夜晚范围及已确认门店事实，不借 Day1 卡片承载。兼容原有已存全程酒店表示，不在本切片重写历史数据。
- 待确认酒店计入已识别、待确认和未处理覆盖；同一项问题不能再计为额外未知地点。确认只消除该对象已解决的问题，其他历史未处理不变。未解决时 `coverage.complete=false`。

## API 与命令

主要位置：`readback.py`、`candidates.py`、`commands.py`、`repository.py`、`app/api/trip_understandings_v3.py`。

- 扩展现有 `GET /supplementary`，仅在 `include_pending_lodgings=true` 时返回当前版本仍待确认的酒店名称、可靠城市提示和随机令牌。默认不返回私有名称。复用所有权、原文有效期和 `Cache-Control: no-store`；不能直接返回最早导入中已经解决的旧项。
- `POST /place-candidates` 兼容待确认酒店目标。保留现有卡片查询契约；新目标凭据绑定资源、当前 ETag、待确认令牌和所选用途／夜晚／位置。搜索本身不改变行程。
- 搜索城市优先采用用户明确选择及可靠原文提示。缺少提示时，仅当目的地与所有已确认地点的非空城市唯一一致才允许跟随行程；跨城、未知或冲突返回 `422 CITY_REQUIRED`，不查询地图。页面提示选择城市、保持已选用途并聚焦城市选择。
- 增加 `LODGING_RECOVER` 命令：待确认令牌、候选凭据、全程／指定夜晚／仅到访三选一。服务端验证字段互斥、现有日期范围、当前对象和候选身份，不接受客户端提供的坐标或门店 ID 作为核验结果。
- 复用现有命令事务、幂等键、If-Match 和不可变版本；确认写入后沿用地图／餐宿建议失效策略。旧版本候选、跨对象候选、重复提交和响应丢失必须正确处理。
- 来源已删除或过期时拒绝恢复提交；搜索后发生删除，也须在写事务中再次检查，不能凭旧候选恢复来源对象。

## 仅到访与住宿约束

- 增加明确的 `VISIT_ONLY` 用途，仅由本切片的用户确认产生。不能用 `lodging_event=None` 表示仅到访：旧兼容逻辑会把 `None` 酒店当作过夜。
- `VISIT_ONLY` 保留用户指定日期和顺序，可参与真实访问路线，不占当晚住宿、不推断前晚，也不生成跨日酒店锚点。
- 仅在用户明确用途并核验门店后，才将全程／指定夜晚写入独立住宿约束；地图和住宿消费者读取该约束。未知对象不进入 `MapRenderPlan.lodging_constraints`，不占据任何夜晚。
- 跨城和已确认酒店保持各自范围；不能按名称、城市猜测扩大或静默缩小用户选择的夜晚。

## 编辑复制与原文删除

- 普通命令、住宿选择及检查建议采纳均复制每日卡片和独立住宿约束，保持公开令牌与已核验身份一致；待确认酒店、餐饮前后位置引用分别重绑。原文有效时另行保留尚未解决的无日期酒店，删除或过期后不复制私有待恢复记录。
- 确认后移除当前待确认引用并产生新的住宿约束／访问卡；历史版本和撤销保持可追踪，不能回读成重复待确认项。
- `_persisted_proposal` 仅保留非原文结构；最小名称引用使用现有可删除源行和加密 source claims。不得加入公共快照、事件、日志、浏览器持久缓存或新独立长期副本。
- 删除原文后，待确认源行、私有名称及引用随现有源删除／到期清理一起移除，私有接口返回 `DELETED` 或 `UNAVAILABLE`。旧结果引用、撤销和迟到响应不得恢复名称。
- 初始识别落库也须在取得数据库锁后按当前时钟复查原文期限；等待期间到期则拒绝产生结果、活动、待恢复酒店或原文证据。
- 用户已确认的独立住宿按既有已确认卡片事实策略保留；`_erase_activity_source_quotes` 的合法保留投影须包含独立住宿约束，不保留未确认名称。

## 验收清单

- 固定回放：补全为空、无效、超时或服务失败后，酒店仍有待确认对象；没有 Day1 假访问，没有未确认主卡，没有新增模型调用。
- 引用反例：其他酒店、另一次同名提及、无名住宿、备选和错误引用不误恢复。
- 三种用途：全程、单晚／多晚、仅到访分别形成正确结果；`VISIT_ONLY` 不占夜晚或推断前晚；未知酒店不限制其他夜晚。
- 编辑与恢复：普通编辑、刷新、重启、撤销、重复提交、响应丢失、并发冲突后，对象、范围、位置和计数一致。
- 候选安全：改变用途／夜晚／位置、旧版本、过期、跨对象或跨资源的候选均被拒绝；失败零写入。
- 覆盖：解决一个对象只减去它的问题，不把其他未处理内容变成完成；无普通主卡时也能保留可恢复的部分结果。
- 隐私：原文删除和到期后，数据库、私有接口、旧版本回读、撤销及迟到候选均不能恢复未确认名称或引用；已确认事实按现有策略保留。
- 内存与 PostgreSQL 整链一致；桌面／手机、键盘操作、取消、刷新和最终真实门店核验通过后再声明完成。
