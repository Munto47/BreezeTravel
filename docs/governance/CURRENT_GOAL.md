## Outcome

让每个非 PASS Finding 都有可执行、可解释且不越过证据边界的 Advice；用户预览并采纳安全 Repair 后，只创建一个新 revision，并在完整 postcheck 后判断是否解决。具体替代地点只能来自冻结 CandidateSet。OR-Tools 只作为实验策略参加固定 bake-off，未过门禁不得进入默认运行时。

```text
AuditFinding → AdviceBundle → 冻结 CandidateSet/筛选条件
→ RepairOption/EditCommand 预览 → 新 ItineraryRevision
→ 完整 postcheck → 新报告与 lineage
```

## Scope

- 补齐 `AdviceBundle` 的 finding 绑定、具体行动、预期影响、不确定性、证据与 trade-off；
- CandidateSet 冻结、地点/路线 receipt 绑定与无可靠候选时的降级表达；
- 统一 RepairEngine 比较 `BoundedRepair`、`RoutingModel/TSPTW` 和实验性 `CP-SAT`；
- 预览、采纳、幂等、revision/CAS、旧报告 stale 与完整 postcheck；
- 固定 36 条 solver bake-off，在首次正式比较前冻结输入、oracle、RunSpec、成本函数和 seed；
- P4 数据合同收敛为 18 pilot、180 dev、72 regression；由开发子代理生成候选案例与变体、独立复核、确定性校验后冻结，同源案例不得跨 split；
- 继续只支持北京、上海、杭州，单城市、2～5 人、2～5 天；复用现有 API/schema 与 migration `024`。

## Non-goals

- 不扩城、不跨城，不新增产品运行时 Agent、消息队列、Kubernetes、GraphRAG 或模型微调；
- 不进入 P5 的 360 全量评测、90 frozen blind、独立 Judge 总评或 Legacy/Core/Solver 最终消融；
- 不修改公共 HTTP API/schema，不新增 migration，不扩大 Provider 来源；
- 不把模型举例写成已验证地点，不承诺最低价、实时客流、自动订票或全局最优；
- 不公网部署、不真人招募、不合并 `main`；G1/G4/G5/G6 候选证据债保持原等级。

## Authority and invariants

- 权威顺序继续遵循 `AGENTS.md`、Charter、Trip Check Spec/API、Program、Roadmap、Release Gates 与已接受 ADR；
- `AuditEngine` 仍是 Finding 唯一权威；LLM/solver 不得自行删除、降级或标记 Finding 已解决；
- 返回具体地点的 Advice 必须 100% 来自冻结 CandidateSet，并绑定地点与路线 receipt；没有可靠候选时只返回搜索区域和筛选条件；
- 每次有语义的采纳必须创建新 revision；旧报告立即 stale；只有新 revision 完整 postcheck 后才显示解决；
- Repair 不得新增 `BLOCKER/HIGH/UNKNOWN`；`UNKNOWN/UNAVAILABLE` 不得改写为 PASS；
- 相同幂等键与相同 payload 只返回原结果；不同 payload 复用键冲突；并发采纳继续由 revision/CAS 拒绝失败方；
- Solver 的目标函数、约束、超时与 fallback 必须版本化并写入 RunSpec/receipt；超时或无解回退不得伪装成 solver 成功。

## Acceptance cases

- 每个 `MUST_ADJUST / SHOULD_OPTIMIZE / NEEDS_CONFIRMATION` Finding 都产生至少一个 Advice，包含行动、预期影响、不确定性和证据边界；
- 具体候选地点来源覆盖率 100%，非 CandidateSet 地点自动进入 `UNVERIFIED_CANDIDATE_REJECTED`；无候选时不编造地点；
- 预览不写 revision；首次采纳恰好创建一个新 revision；重复采纳幂等 replay；并发/stale 采纳返回 409 并回读胜者；
- 新 revision 自动执行完整 postcheck，旧 report stale；新增 `BLOCKER/HIGH/UNKNOWN` 数为 0；
- fixed 36 bake-off 对三种策略使用相同 RunSpec/oracle，输出成功率、失败类、P95、编辑成本、路线代价、timeout/fallback 和 replay hash；
- CP-SAT 只有在安全条件全部满足，且相对 BoundedRepair 成功率提高至少 10 个百分点或稳定解决至少 3 类其无法解决的问题，并满足 5 天 25 站 P95 ≤2 秒时，才可进入默认运行时；否则保留实验资产；
- 18 pilot 持续通过；180 dev 与 72 regression 结构、三城/难度/故障分布、同源隔离和隐私扫描全部通过；frozen blind 保持 0。

## Milestones

1. 基线与失败矩阵：审计现有 Advice/Repair/CandidateSet 代码和证据，冻结 36 条 bake-off 合同，不先改 solver；
2. Advice 与 CandidateSet：补齐 AdviceBundle 和 fail-closed 候选来源，完成无候选降级；
3. Repair 事务闭环：预览、采纳、revision/CAS、幂等、stale 与完整 postcheck；
4. 数据工厂：开发子代理生成 180 dev/72 regression，独立复核并执行 split/重复/隐私/分布验证；
5. Solver 实验：在相同 36 条上运行 BoundedRepair、RoutingModel/TSPTW、CP-SAT，先判安全再比较效果和性能；
6. P4 Gate：同 commit 重跑 PostgreSQL、浏览器恢复、完整回归、P1/P2/P3 regression、bake-off 和 evidence readback。
