## 2. 建议定稿的产品愿景

### 2.1 一句话定位

> BreezeTravel 是面向朋友和家庭小团体的可验证行程决策工作台：把已有攻略或旅行想法转成真正能走、满足同行人硬约束、每次判断与修改都有证据的可确认行程。

### 2.2 核心用户与首期范围

- 核心用户：为朋友或家庭承担规划、核验和协调压力的旅行组织者；
- 团体规模：2～5 人；
- 行程长度：2～5 天；
- 首期城市：北京、上海、杭州；
- 首期场景：国内城市自由行，优先验证已有行程的体检与最小修复。

扩大城市、人群或旅行类型不是自然延伸，必须由真实用户证据和独立 Goal 批准。

### 2.3 用户最终得到什么

用户不只得到一份生成文本，而是得到一个可以确认的行程版本，其中：

1. 地点已经消歧并保留来源；
2. 营业、交通、时间、天气和成员约束有可追溯事实；
3. 无法确认的事实保持 `UNKNOWN`；
4. 风险按必须修改、建议调整、待确认分组；
5. 修复方案可以比较、预览、拒绝、应用和撤销；
6. 修改产生新 revision，旧报告失效并重新完整验证；
7. 同行人可以查看影响、表达意见并锁定确认版。

### 2.4 北极星结果

> 用户用更短时间得到一份已确认关键风险、满足成员硬约束、可以实际执行的行程版本。

优先衡量：首次确认所需时间、硬约束漏检率、有效修复采纳率、报告分享或复用率，以及真人对关键 finding 的准确性判断。Agent 数量、生成地点数量、测试数量和“发现问题的比例”不能单独作为产品成功指标。

## 3. 产品结构：双入口、单核心

### 入口 A：已有行程体检

```text
文本/模板导入 → 地点消歧 → Evidence → Audit → Repair A/B
→ 新 Revision → 完整复验 → 确认版
```

这是首个用户价值入口，也是短期 MVP 的优先入口。

### 入口 B：从零构建路线

```text
搜索真实起点 → 下一站 SuggestionSet → 接受/拒绝
→ 连续构建 → 拖拽或按钮编辑 → 增量审计 → 完整复验
```

入口 B 在事实、版本和验收底座稳定后推进，不得为了展示“AI 生成”绕过 Evidence 或 Audit。

两个入口在形成 `ItineraryRevision` 后必须共用同一套 Evidence、Audit、Repair、成员约束、确认和版本模型，禁止维护双套规则或状态。

## 4. 短期、分阶段和长期目标

阶段以用户闭环和证据定义，不以目录存在、代码行数或测试数量定义。Final 2.0 的 P0～P8 是实施工作包；以下 M1～M4 是产品 milestone，两者不得混作同一套进度百分比。

### M1-foundation：已有行程可验证闭环

目标效果：用户能导入一份真实行程，解决地点歧义，看到有依据的风险，选择最小修复，并获得重新验收的新版本。

实现主线：revision/hash 持久化 → 导入与候选事实连续性 → Evidence Collector → 唯一 Audit Engine → 有限 Repair → postcheck → confirm。

完成约束：必须有真实 HTTP 产品链、本地 PostgreSQL 回读、刷新/重启恢复、并发与幂等测试；fixture 通过不能替代真实 Provider 或真人证据。

### M2-eval：可重放的持续验收闭环

目标效果：每次 Prompt、模型、规则、排序或 Provider 配置变化，都能在相同输入和门禁下与 Baseline 比较，并明确 PROMOTE 或 REJECT。

实现主线：RunSpec → 冻结输入和配置 → 产品路径执行 → case ledger → 独立 Judge → bad-case registry → promotion/rollback。

完成约束：缺 commit、config、dataset、model、receipt 或 postcheck 的 case 必须 `INVALID/UNSCORED`；开发集、回归集、frozen blind、自动 Judge 和真人标签严格隔离。

### M3-builder：从一个真实地点连续形成可验收路线

目标效果：用户从空白状态搜索真实起点，连续接受下一站候选，通过拖拽或移动按钮调整，并始终看到最新审计状态。

实现主线：Anchor/插入边查询 → 冻结 SuggestionSet → 排序解释 → 原子接受 → 反馈账本 → Undo → 增量审计 → 完整复验。

完成约束：客户端不得伪造 canonical POI；远距离或证据不足候选不得静默隐藏；拖拽不能直接改最终状态或跳过服务端 revision。

### M4-beta：成员协同与受控三城 Beta

目标效果：真实组织者能让成员填写硬约束、查看方案取舍、共同确认，并在临行前看到事实变化；公网双入口可重复完成。

实现主线：成员约束 → 权限和分享 → 冲突处理 → 临行复检 → 真人校准 → 公网 E2E → 发布证据包。

完成约束：自动代理不能代填真人证据；本地、snapshot、live Provider、公网和 user validation 分层报告。达到这一阶段前不得宣称“受控三城 Beta 已验证”。

### 长期方向：只有前置证据支持后再启动

- OCR、截图、群聊和授权内容导入；
- 出发前 24～48 小时和手动触发的当天局部重排；
- 将稳定且被真实使用的验证能力抽成 API/SDK；
- 基于许可、撤回机制和真实反馈建立内容与规则飞轮。

这些不是当前承诺：全国或全球覆盖、实时排队与精确人流、医疗安全、全量无障碍、全平台最低价、自动代订、全旅程主动监控、通用全能旅行 Agent。

## 5. 不可弱化的实现不变量

- `UNKNOWN` 不得变相计为 PASS；证据不足必须向用户暴露。
- 每次有语义的编辑必须创建新的服务端 revision，并使旧报告 stale。
- Audit Engine 是唯一规则权威；不得为 Planner、导入和前端各维护一套冲突规则。
- Repair 必须可预览、可拒绝、可撤销，并在应用后执行完整 postcheck。
- 锁定预约、成员硬约束和用户已确认的承诺不得被静默删除。
- Provider 失败不能回退成合成真实 POI；部分失败要保留成功事实并标明降级范围。
- 服务端只信任冻结的 canonical 数据、revision 和幂等命令，不信任客户端回传的事实。
- controlled fixture、source prior、snapshot、live Provider、自动 Judge、公网 E2E 和真人证据是不同证明层，不能互相替代。
- 任何优化必须能绑定 RunSpec、Baseline、指标、成本和失败样本；不能只凭演示观感晋级。

## 6. 每个开发 Goal 的强制合同

正式开发前应将以下内容写入 Goal 或阶段说明：

1. `Outcome`：本轮结束后用户能完成什么；
2. `Scope`：唯一 milestone、允许修改的模块和数据；
3. `Non-goals`：本轮明确不做的功能、城市、Provider 和基础设施；
4. `Authority`：适用的 Charter、Final 章节、ADR、schema 和 API contract；
5. `Baseline`：branch、commit、dirty tree、现有测试和已知红灯；
6. `Invariants`：本轮不能破坏的领域和证据边界；
7. `Verification`：定向测试、完整回归、浏览器路径、回读和 evidence gate；
8. `Budget`：最长执行窗口、外部 API/模型成本和允许重试次数；
9. `HITL`：需要人工批准的事件；
10. `Stop conditions`：失败、矛盾、范围扩大或证据缺失时何时停止。

一个 Goal 只完成一个 milestone 中的一个可审查切片。不得使用“持续优化直至完成整个方案”作为开发合同。

## 7. 必须人工决定的节点

以下变化不能由实现 Agent 自行解释或批准：

- 修改产品愿景、目标用户、首期城市、阶段顺序或非目标；
- 进入下一个 milestone，或把阶段状态从实现提升为集成、live、公网或真人验证；
- 修改公共 API、核心数据契约、数据库 migration 或规则权威；
- 新增生产依赖、外部数据源、付费模型、真实 Provider 调用或预算；
- 修改测试 oracle、Gate 阈值、frozen blind、证据等级或把失败改为例外；
- 外部数据许可、用户隐私、授权保存和撤回路径；
- merge、生产 migration、deploy、release 和公开产品能力声明。

普通切片内的实现、定向测试以及向开发分支 commit/push，按全局 Git/GitHub 规范执行，不需要把每次文件修改都变成人工审批。

## 8. 定稿前必须消除的口径冲突

1. 根 `README.md` 与 `AGENTS.md` 仍把 LangGraph、RAG、Planner 和通用生成式助手当作产品中心；需要改成“现有可复用资产”，不能继续充当产品愿景。
2. 市场调研把“已有行程体检”定义为 MVP 主入口，Final 2.0 同时设计双入口；应明确入口 A 先闭环、入口 B 后建设，而不是同一阶段并行扩张。
3. P0～P8 和 M1～M4 同时存在但语义不同；应固定 P 为实现工作包、M 为用户/产品 milestone，并给出唯一映射表。
4. “代码已存在”“测试通过”“能力已验证”在旧文档中仍有混写；所有状态应改用计划、实现、单元、集成、snapshot、live、公网、真人八级证据。
5. 短期优先级需要从“继续补功能”改成“让入口 A 的真实用户闭环和验收闭环同时可复现”，再推进 Builder 和 Beta。
